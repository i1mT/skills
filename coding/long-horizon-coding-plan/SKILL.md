# 长期代码改动计划

把大型代码改动整理成一组可以由 AI coding agent 持续执行、跨会话恢复并且逐阶段验收的仓库内 Markdown 文档。

## 核心结果

计划不是一次性的说明文档，而是后续实施过程的控制面。它应当同时做到：

- 新会话只读取导航和进度文档，就能知道项目现状、目标、下一步和阻断。
- 每个阶段具有明确边界、依赖、实施事项、验证方案和完成门禁。
- 实际进度、证据、偏差和决策只有一个事实源，避免阶段文档互相矛盾。
- 计划基于仓库真实代码与文档，而不是依据用户描述猜测架构。
- 后续 Agent 可以连续实施，不需要用户反复回复“继续”。

## 工作流程

### 1. 读取仓库规则

先查找并完整读取适用的 `AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING.md`、计划规范和相关架构文档。沿着目录规则继续读取直接引用的必要文档。

确认以下约束：

- 计划文档应当保存在哪里，以及日期和目录如何命名。
- 是否存在长期进度、Todo、GEB 或目录导航机制。
- 文件长度、单层文件数量、语言、测试和 Git 要求。
- 哪些文档是产品、架构、数据模型或运行契约的事实源。

### 2. 调查当前实现

使用只读工具检查与改动相关的代码、测试、配置、数据库、接口和现有计划。优先搜索真实标识符、入口函数、状态模型和调用链。

在编写计划前形成以下证据：

- 当前行为和已有能力。
- 目标行为与当前行为之间的差距。
- 必须保持的兼容行为和安全边界。
- 受影响的模块、数据、接口、界面、后台任务和文档。
- 可以复用的现有机制，以及需要替换或迁移的旧机制。
- 关键风险、未知事项和需要实测才能确认的假设。

如果证据不足，继续调查。只有当不同答案会实质改变方案，并且无法从仓库或只读检查中获得答案时，才询问用户。

当当前行为、主要调用链、受影响模块、兼容边界和关键未知事项都已经能够支持阶段决策时，停止扩大调查并开始编写计划。计划阶段不追求枚举所有调用点；把完整 inventory 作为阶段 01 的可验证 Todo，可以避免调查无限延长。

### 3. 确定计划边界

明确记录：

- 最终目标和可观察的完成条件。
- 范围、非目标和不允许破坏的行为。
- 核心架构决策及其原因。
- 实施顺序中的依赖关系。
- 哪些事项需要 feature flag、数据迁移、兼容读取或回滚方案。

不要把尚未确认的推测写成既定事实。将其标记为风险、待验证假设或阶段 01 的调查事项。

### 4. 划分阶段

按照可独立验证的架构增量划分阶段，而不是按照文件夹、团队或笼统主题拆分。推荐顺序如下，并根据任务调整：

1. 契约、现状基线和评测能力。
2. 核心模型、数据结构或基础抽象。
3. 主要业务路径和兼容迁移。
4. 持久执行、异常恢复或复杂集成。
5. 可观测性、界面、运维和安全加强。
6. 全量验收、分阶段发布和旧机制清理。

阶段数量通常为 3–7 个。每个阶段都应当能够单独提交和验证；后续阶段不能依赖没有证据的“前面应该已经完成”。

只有真正的实施阶段使用 `01-`、`02-` 等连续编号。不要把现状说明、目标架构或 Agent 执行手册编号成阶段；把长期需要的信息并入 `progress.md`、`AGENTS.md` 或无编号的参考文档，避免阶段状态表与文件编号产生两套含义。

### 5. 创建文档集合

优先遵循仓库已有命名。没有既有规范时，创建：

```text
<plan-root>/<YYYY-MM-DD>/<topic>/
├── AGENTS.md
├── progress.md
├── 01-<stage>.md
├── 02-<stage>.md
└── ...
```

使用 [`references/plan-templates.md`](references/plan-templates.md) 中的结构。若阶段较多并触及仓库的单层文件数量限制，应当减少阶段数量或规划子目录，而不是违反仓库规则。

文档职责必须分离：

- `AGENTS.md`：计划入口、文件导航和维护规则。
- `progress.md`：状态、Todo、决策、风险、阻断、证据和实施偏差的唯一事实源。
- 阶段文档：阶段目标、范围、方案、实施事项、测试和完成门禁；不复制动态状态。

计划刚创建时，未实施事项应当使用 `pending` 和未勾选 Todo。不要因为计划已经写完，就把代码实施阶段标记为完成。

### 6. 接入仓库导航

更新必要的上级计划索引、当前状态或目录入口，让后续 Agent 能够发现这组文档。只更新与该计划有关的导航内容，不覆盖其他人的计划和状态。

如果仓库使用 GEB 或类似机制，按照其规则同步 Entry 文档。不要在多个地方复制同一份动态进度。

### 7. 验证文档

至少检查：

- 所有文档非空、标题正确、内部相对链接可解析。
- `progress.md` 包含目标、完成条件、阶段状态、Todo、决策、风险和验证记录。
- 每个阶段包含目标、范围或非目标、Todo、测试方案、完成门禁和交付物。
- 阶段编号连续，导航顺序与依赖一致。
- 所有编号文件都是可实施、可验收的阶段，不存在 `00-` 或只提供背景说明的伪阶段。
- 没有把计划完成误写为实现完成。
- 没有超过仓库文件长度和目录文件数量限制。
- Git diff 只包含计划和必要导航变化，没有覆盖无关工作。

可以使用本 Skill 自带的检查器：

```bash
python3 scripts/validate_plan.py <plan-directory>
```

该脚本只能完成结构检查。仍需人工检查技术内容是否符合真实代码、各阶段能否执行、门禁是否可以验证。

### 8. 完成交付

遵守仓库 Git 规则；如果要求修改后提交，则只提交本次计划相关文件。

最终回复应当提供：

- `progress.md` 和计划入口的可点击路径。
- 阶段列表和每个阶段的简短目标。
- 已执行的结构、链接和 Git 检查。
- 提交记录（如果已经提交）。

## 计划质量原则

### 以证据驱动计划

计划中的“当前状态”应当引用真实模块、接口、表、测试或命令。不要生成任何仓库都适用的通用清单来代替调查。

### 让完成条件可判定

“功能正常”“完成重构”“加强测试”不是门禁。使用能够被命令、状态、指标或用户流程证明的条件，例如：

- 旧表和新表双读迁移测试通过，并且回滚演练能够恢复旧读取路径。
- 三类代表场景完成端到端验收，保存输入、输出和 trace 证据。
- 所有调用方迁移后，静态搜索只剩兼容层中的旧接口引用。

### 分离计划与事实

阶段文档描述打算如何实施；`progress.md` 记录实际上发生了什么。实施中发现方案变化时，先在进度文档记录决策和偏差，再修改受影响阶段。

### 保护跨会话恢复

`progress.md` 必须让下一位 Agent 不依赖聊天记录也能继续。Todo 应当说明对象和验收结果，验证记录应当包含日期、命令或证据以及结果，阻断应当说明恢复条件。

### 计划完整而不过度设计

覆盖产品行为、架构、数据、迁移、安全、测试、可观测性、发布、回滚和文档中与任务实际相关的部分。没有相关性的领域不应为了模板完整而强行加入。

## 禁止事项

- 不要在没有阅读代码的情况下直接生成阶段文档。
- 不要创建只有一个巨大 checklist 的单文件计划。
- 不要让每个阶段维护各自的动态进度副本。
- 不要将代码实现和“编写计划”混在同一次任务中，除非用户明确同时要求实施。
- 不要使用模糊门禁或依赖模型自我声明完成。
- 不要覆盖用户已有的未提交修改。
- 不要通过缩减测试、删除失败证据或隐藏未知事项来宣称阶段完成。
