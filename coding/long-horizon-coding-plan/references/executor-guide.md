# 实施 Agent 执行手册

本文件面向负责**实施**计划（而不是编写计划）的 AI coding agent。计划文档创建完成后，实施者应当把计划目录当作控制面：只读取必要信息、持续落盘状态、按门禁验收、保持与最初方案一致。

## 0. 适用对象与读取时机

- 实施任意编号阶段（`01-*.md` 等）之前读取本文件。
- 编写计划时不需要本文件；本文件不改变计划文档的结构要求。

## 1. 每次会话的启动流程（Boot Sequence）

不要依赖聊天记录或上一次会话的记忆。按以下顺序读取：

1. 读取计划目录的 `AGENTS.md`：文件导航、执行规范、维护规则。
2. 读取 `progress.md`：阶段状态表、Todo、当前阻断、最近验证记录、实施偏差。
3. 只读取当前 in_progress 或下一步要进入的阶段文档；**不要**重读全部阶段文档。

只读以上内容即可开始工作。发现阶段文档与 `progress.md` 矛盾时，以 `progress.md` 记录的事实为准，并把矛盾记入实施偏差。

## 2. 上下文预算（Context Budget）

上下文是执行期最稀缺的资源；失忆通常不是模型问题，而是上下文被无关内容占满：

- 不要一次性读取所有阶段文档、架构文档或整个代码库。
- 用搜索（grep/检索）定位具体标识符、入口和调用链，只读相关片段。
- 关键结论、决策、证据**落盘到 `progress.md`**，而不是只留在对话里；一旦 compact 或截断，对话里的内容会丢失。
- 阶段文档中与当前工作无关的章节，等需要时再读。

## 3. 检查点纪律（Checkpoint Discipline）

按「可验证单元」推进，而不是按「做完整个阶段」推进。每完成一个可验证单元：

1. 运行该单元的测试或验证命令。
2. 将结果（命令、证据、结论）追加到 `progress.md` 的验证记录。
3. 更新 Todo 勾选状态和阶段状态。
4. 如果仓库要求提交，则创建一次独立的提交。

这样即使会话中断、compact 或进程被杀，下一次会话也能从最后一次落盘的状态继续，而不是从零开始。

## 4. 阶段完成流程

完成一个阶段时：

1. 对照该阶段文档的「完成门禁」逐条验证，保存证据（命令输出、测试结果、状态变化）。
2. 确认「输出契约」中的交付物齐备、格式与位置符合约定。
3. 更新 `progress.md`：阶段状态改为 completed，记录验证证据与交付物位置。
4. 提交代码与进度文档。
5. 有条件时创建 sub-agent 按审核清单审核本阶段；审核发现 P0 问题或与计划不符，打回修改，并把阶段状态改回 in_progress。

只有门禁证据齐备才能标记 completed；禁止用「功能正常」「测试通过」这类无法判定的表述自我声明完成。

## 5. 计划即契约（Plan as Contract）

- 最初批准的目标、范围、完成条件和核心架构决策是契约，**未经记录不得擅自更改**。
- 实施中发现更优方案时：先写入 `progress.md` 的「核心决策」或「实施偏差」——说明原计划、实际选择、原因和影响——再修改受影响的阶段文档。
- 不要为了「看起来更顺」而悄悄缩小范围、跳过非目标或弱化门禁。
- 每个阶段结束、以及整个计划结束时，对照最初的「目标」和「完成条件」逐条复核，而不是对照「最近一次对话」。

## 6. 上下文告急或中断前（Compact / Resume / 退出）

在以下任一情况发生前，先完成一次落盘：

- 上下文接近窗口上限，准备 `/compact` 或类似压缩；
- 会话被中断、超时或需要退出；
- 需要把任务交接给另一个会话或另一个 agent。

落盘内容至少包括：当前阶段、已完成单元及证据、未完成 Todo、下一步动作、未决问题与阻塞。完成后按 `recovery-protocol.md` 的恢复流程继续。

## 7. 并行子任务（如适用）

当计划允许并行子任务时，为每个子任务写明：目标、输出格式、允许使用的工具/来源、边界（哪些不做）。子任务之间通过文件系统交换产物，不通过对话搬运大段内容，避免「传话游戏」导致信息失真。并行任务的审核结果回到主流程的 `progress.md` 统一记录。
