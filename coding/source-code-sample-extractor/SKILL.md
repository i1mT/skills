# 源码评估样例抽取

从现有代码仓库中制作一个体积较小、不可独立复刻产品、但足以让潜在客户判断代码质量的源码样例目录。

## 目标结果

- 默认创建 `code-sample/`，除非用户指定其他目录。
- 默认选择 3 个代码文件；用户要求更少时可以选择 2 个。
- 使用单层目录，不复制原仓库的目录结构。
- 代码样例应当能够展示真实工程能力，但不能组合成可运行的完整产品。
- 不修改原始业务文件，只在样例目录中创建经过整理的副本。

## 工作流程

### 1. 读取仓库规则

先查找并完整读取适用的 `AGENTS.md`、`CLAUDE.md`、README 和项目配置，遵循仓库已有的文件组织、验证和 Git 要求。

检查 `git status`。已有修改属于用户，不能覆盖、删除或混入无关改动。如果目标目录已经存在，先检查其中内容；除非用户明确授权，不要直接覆盖。

### 2. 了解项目结构

使用 `rg --files`、入口配置和关键模块快速了解：

- 前端框架、后端框架、主要语言和数据库方案。
- UI、状态管理、通用业务逻辑、API、实时通信和基础设施模块。
- 文件规模、内部依赖以及各模块是否包含核心产品逻辑。

抽取样例需要基于真实代码，而不是仅依据文件名或用户描述猜测。

### 3. 先检查泄露风险

在选择文件前检查工作树和 Git 跟踪文件中的风险内容：

- `.env`、证书、私钥、Token、云服务密钥和数据库连接信息。
- 用户数据、附件清单、Seed 数据、生产 SQL、日志和导出文件。
- 内部域名、IP、账号、Bucket、Webhook 和第三方凭据。

如果发现疑似真实密钥，只报告文件位置和风险类型，不要在对话或样例中重复密钥值。提醒用户优先吊销或更换密钥；不要未经授权改写 Git 历史。

### 4. 选择 2 至 3 个样例

优先选择能够覆盖不同工程层次的组合：

1. 一个前端交互组件，展示 Props、状态、边界处理和交互设计。
2. 一个无副作用的业务工具，展示类型设计、解析、转换或校验逻辑。
3. 一个后端业务服务，展示输入规范化、权限检查、transaction 和依赖边界。

候选文件应当满足：

- 单个文件通常为 50 至 200 行，动态语言文件不得超过 400 行。
- 代码意图清楚，能够独立阅读，没有明显安全缺陷或坏味道。
- 样例之间存在技术覆盖差异，而不是三个相似的 UI 或工具文件。
- 即使客户拿到全部样例，也无法还原数据库结构、认证系统或完整业务链路。

不要选择：

- 认证算法、权限策略全集、数据库 Schema、迁移或生产数据。
- WebSocket 服务入口、MCP 工具全集、支付、计费或其他核心算法。
- 部署脚本、云服务实现、OpenAPI 全量定义、环境配置和锁文件。
- 自动生成代码、第三方代码、调试脚本以及存在已知安全问题的实现。

### 5. 整理与脱敏

样例应当来自真实实现，同时可以进行必要整理：

- 删除与展示目的无关的分支、字段和内部注释。
- 使用接口或函数参数替换数据库、通知、对象存储等内部依赖。
- 将内部域名、业务名称、路径、用户标识和基础设施常量替换为通用表达。
- 保留原有关键语义和设计思路，不要编造与真实项目不一致的架构。
- 保证样例内部类型一致；能够独立检查的文件应当通过严格类型或语法检查。

可以在代码文件顶部加入简短的评估用途声明，但不要添加冗长法律文本。

### 6. 创建极简目录

默认结构如下：

```text
code-sample/
├── README.md
├── frontend-sample.tsx
├── domain-sample.ts
└── backend-sample.ts
```

不要创建子目录、运行脚本、`package.json`、环境文件或额外文档。

使用 3 个样例文件时，`README.md` 只写下面这句话，不添加标题、技术概览、文件说明或使用限制：

```markdown
本目录包含三个经过脱敏处理的项目源码样例，仅用于技术评估。
```

如果用户明确要求 2 个文件，将“三个”替换为“两个”。用户提供其他文案时，以用户文案为准。

### 7. 验证交付物

完成后逐项检查：

- 目录中只有一个 README 和 2 至 3 个代码文件。
- 没有嵌套目录、配置、数据、密钥、内部地址或完整基础设施实现。
- README 的文件数量与实际样例数量一致，并且保持一句话。
- `git diff --check` 通过，原始业务文件没有发生变化。
- 无框架依赖的样例通过严格类型检查；前端样例至少通过 TSX 语法构建检查。
- 样例总量适合直接压缩发送，不包含 `.git` 或任何 Git 历史。

全仓库验证如果因为既有问题或缺少依赖而失败，应当区分样例错误与环境错误，并对样例执行独立检查。

### 8. 向用户报告

说明样例目录位置、包含的文件、各文件代表的工程层次和验证结果。安全问题单独说明，不要把风险细节写入客户可见的 README。

只有用户明确要求或仓库规则要求时才提交 Git；提交时只包含本次 Skill 创建的样例目录或文档，不混入用户已有修改。

## 完成标准

只有同时满足以下条件才算完成：

- 样例来自真实项目并经过必要脱敏。
- 客户能够判断前端、业务逻辑或后端代码质量。
- 样例无法独立运行，也不足以复刻核心产品。
- README 保持一句话，目录保持单层且文件数量正确。
- 敏感信息检查和独立代码检查均已完成。
